  • First: the IR compatibility layer plus instcombine and dce.

  That is the right starting slice because it gives us the debugging loop we need before touching harder LLVM pieces.

  Concrete first target:

  1. LLVM-compatible IR import/print
      - Parse a small subset of LLVM IR text.
      - Represent functions, basic blocks, SSA values, integer types, add, sub, mul, ret.
      - Print normalized LLVM-compatible IR.
  2. Verifier
      - Check SSA references exist.
      - Check instruction operand types match.
      - Check every block ends with a terminator.
      - Check def-use consistency.
  3. Pass manager
      - Run named passes.
      - Print before/after.
      - Report changed/unchanged.
      - Support --passes=instcombine,dce.
  4. instcombine subset
      - x + 0 -> x
      - 0 + x -> x
      - x - 0 -> x
      - x * 1 -> x
      - 1 * x -> x
      - constant folding
  5. dce subset
      - Remove unused pure instructions.
      - Keep terminators and side-effecting instructions.

  The first comparison should be:

  opt -passes=instcombine,dce pre.ll -S -o llvm_after.ll
  z_llvm --passes=instcombine,dce pre.ll -o zig_after.ll

  Then compare normalized llvm_after.ll and zig_after.ll.

  After that, the next LLVM pieces should be:

  1. simplifycfg
  2. early-cse
  3. mem2reg
  4. dominator tree
  5. loop analysis
  6. LICM

  So the first real reproduction target is not machine code yet. It is: LLVM IR compatibility + pass infrastructure + two simple scalar cleanup passes.

• Yes: the structure is directionally right for a small, comparison-driven LLVM replacement prototype. It has the right early pieces: IR core, pass manager, analysis modules, individual pass
  modules, opt-style fixtures, and docs requiring upstream LLVM mappings.

  The main caveat is scope. The stated project goal in docs/Zig_LLVM_pass_pipeline_plan.md:3 is full LLVM-backend replacement, but the code is currently a middle-end IR/pass prototype. There
  is not yet src/target/, src/codegen/, src/mc/, src/debug/, src/bitcode/, or the planned API inventory from docs/Zig_LLVM_pass_pipeline_plan.md:43. That is fine for the current phase, but
  it should be treated as phase-zero infrastructure, not as a backend replacement yet.

  What looks good:

  - The docs correctly insist on LLVM as the reference and semantic comparison, not a line-for-line port.
  - The current code layout is clean: src/ir.zig, src/analysis/*, src/passes/*, src/pass_manager.zig, and test/opt/*.
  - The comparison flow in scripts/compare_opt.sh:20 is the right discipline: run z_llvm, run opt-22, normalize both, diff both.
  - docs/next_steps.md is usefully incremental and keeps the active work small.

  Main concerns:

  - src/ir.zig:156 is already becoming a large monolith. The plan calls for src/ir/parser.zig, print.zig, and verify.zig; splitting that soon would reduce friction.
  - src/pass_manager.zig:22 is intentionally tiny, but the long-term plan needs function/loop pass managers, analysis caching, invalidation, timing, and pipeline aliases.
  - Docs and code appear slightly out of sync around select: docs/unsupported_ir.md still lists select as unsupported, while the source/tests now contain select handling.
  - The missing LLVM API inventory is important. Without it, it is easy to build an optimizer toy that does not converge on the actual Zig LLVM dependency surface.

  My recommendation: continue the current approach, but make the next structural milestone “inventory + IR split,” not another pass. Finish select, update the docs, then create docs/
  inventory/zig_llvm_api_inventory.md and start carving src/ir.zig into parser/printer/verifier files. That keeps the project aligned with the real replacement goal instead of drifting into
  an isolated LLVM-IR optimizer subset.
